# T-093 · Единый формат ошибок API и понятные сообщения на фронте

- **Приоритет:** high — до сезона обязательно
- **Область:** Баги домена / API / UX
- **Создана:** 2026-10-21

## Контекст

При нарушении контракта ответа API `typed-openapi` выбрасывает ошибку Zod, а глобальный обработчик фронта показывает её `error.message` целиком. Сотрудник видит технический JSON с `invalid_format`, регулярными выражениями и путями полей (пример: даты в карточке возврата T-028). Даже если конкретное несоответствие контракта исправлено, такой же экран возможен при следующей ошибке ответа.

Сейчас `apps/crm-frontend/src/utils/handleError.ts` возвращает сырое `Error.message`, а `apps/crm-frontend/src/app/queryClient.ts` показывает английские заголовки `Data upload error` и `Operation error`. На backend `apps/backend/src/common/pipes/zod-validation.pipe.ts` возвращает `Validation failed` и вложенное дерево `errors`; `apps/backend/src/common/filters/prisma-client-exception.filter.ts` обрабатывает только часть ошибок Prisma. Нужно определить один предсказуемый формат ошибок API и не показывать сотруднику внутренние диагностические данные.

## Критерии готовности

- [x] Определён и описан в `.agents/shared-api.md` единый формат ошибочного ответа API: код/статус, короткое русское сообщение для сотрудника и, где полезно, ошибки конкретных полей. Сохранена совместимость с `typed-openapi` и статусами, уже описанными в TypeSpec.
- [x] Валидация входных данных, Nest-исключения и известные ошибки Prisma отдают этот формат; неожиданные ошибки не раскрывают внутренние детали клиенту и остаются доступными в серверных логах/Sentry.
- [x] Проведён аудит контроллеров и сервисов: убраны сырые сообщения библиотек и неоднородные тела ошибок там, где они попадают в интерфейс. Доменные причины ошибок остаются конкретными и на русском.
- [x] Фронт централизованно различает ожидаемую ошибку API, ошибку сети и нарушение контракта запроса/ответа. Для нарушения контракта показывает короткое русское сообщение и оставляет детали в консоли/Sentry; заголовки уведомлений на русском.
- [x] Отдельные поля формы получают понятную ошибку, если backend её прислал; существующее подавление ожидаемых 401 и обновление токена работают как прежде.
- [x] Есть тесты backend и frontend для 400/409/500, ошибок полей, сетевого сбоя и Zod-ошибки ответа. Ни один из них не выводит пользователю JSON, regex или stack trace.

## План

1. Зафиксировать форму error response в `shared/api-spec/common/errors.tsp`, перегенерировать typed-openapi-клиент и проверить, что существующие HTTP-статусы и auth refresh сохраняются. Обязательные `statusCode`/`message` не ломать; новые машинный код и ошибки полей сделать необязательными.
2. На backend нормализовать HTTP-исключения, Zod validation, известные ошибки Prisma и неожиданные 500 в одном месте. Для ожидаемой ошибки сохранить её HTTP-статус и русское сообщение; для неожиданной скрыть внутренние детали от клиента и оставить их в логах. Не допустить двойного ответа от фильтров.
3. На frontend в `handleError` различать типизированную ошибку API, сетевой сбой, Zod-проверку контракта и неизвестное исключение. Отображать короткий русский текст, заменить английские заголовки в `queryClient`, проверить локальные уведомления и форму. Техническую диагностику оставлять разработчику.
4. Проверить реальные ошибки по всем модулям backend: auth, клиенты/дети, костюмы, визиты, уведомления. Исправить сырые сообщения библиотек и неоднородные ответы, не меняя бизнес-правила. Добавить тесты на 400/401/404/409/500, ошибки полей, сетевой сбой и Zod-ошибку успешного ответа.
5. Прогнать shared build, typecheck/lint всех изменённых пакетов, unit/integration/frontend тесты и ручной сценарий в браузере на десктопе и 375 px.

## Распределение работы

- **Агент контракта и backend:** `shared/api-spec/common/errors.tsp`, генерация `shared/src/openapi-client*` и ручные экспорты при необходимости; `apps/backend/src/common/filters/`, `pipes/zod-validation.pipe.ts`, регистрация в `main.ts`, прямые и integration-тесты этих границ. Не меняет доменные сервисы и frontend.
- **Агент frontend:** `apps/crm-frontend/src/utils/handleError*`, `src/app/queryClient*` и необходимые локальные обработчики/тесты. Опирается на совместимые `statusCode`/`message` и необязательные `code`/`fieldErrors`; не редактирует `shared` и backend.
- **Принимающий агент:** аудит сообщений контроллеров/сервисов остальных модулей, проверка пересечений с T-092, сквозная приёмка и ручная проверка интерфейса.

## Принятые решения для реализации

- Сохраняем совместимые обязательные поля существующего `Common.Error`: `statusCode: number` и `message: string`. Дополнительные машинный `code` и ошибки полей (`fieldErrors`) — необязательные; поле `error` остаётся совместимым на время перехода. Точную запись этих типов сначала проверяем генерацией TypeSpec/OpenAPI/typed-openapi, не правим generated-файлы вручную.
- Для ожидаемых 4xx backend возвращает короткое русское `message` с конкретной причиной и прежний HTTP-статус. Для неожиданного 500 клиент получает общее русское сообщение; подробности остаются в серверном логе/Sentry без вывода секретов и персональных данных в ответ.
- Единая нормализация на HTTP-границе Nest покрывает Nest-исключения, Zod validation и известные ошибки Prisma. Существующий `PrismaClientExceptionFilter` нужно встроить в эту схему без двойной обработки. Не переписывать каждый контроллер только ради одинаковой оболочки ответа; сервисы сохраняют конкретные доменные причины.
- Frontend различает `TypedStatusError`/Axios с корректным ответом API, сетевую ошибку и `ZodError` при проверке запроса либо ответа. Сотруднику показываются короткие русские сообщения; детали Zod доступны разработчику в console/Sentry. Не выводить `Error.message` произвольного исключения без проверки: он может содержать JSON, regex или stack trace.
- Сохраняем обновление токена и подавление ожидаемых 401. Не создаём второй toast в локальном обработчике, если ошибку уже показывает глобальный `QueryClient`. Поле формы подсвечиваем только там, где есть соответствующий `fieldErrors`.
- Порядок делегирования: сначала один исполнитель закрепляет и генерирует контракт `shared`, затем backend и frontend можно делать параллельно. T-092 завершена; `visit-order.service.ts` теперь переводит доменные ошибки в HTTP и входит в аудит сообщений T-093. Финальная сквозная проверка и аудит остаются у принимающего агента.

## Результат

Реализован общий `Common.Error` (`statusCode` и `message` обязательны, `error`, `code`, `fieldErrors` необязательны), общий HTTP-фильтр Nest и безопасная обработка ошибок на фронте. Старый Prisma-фильтр и дублирующий Sentry-перехватчик удалены; неожиданный 500 попадает в Sentry один раз без явной передачи тела запроса. Аудит пользовательских HTTP-сообщений завершён, английские сообщения идемпотентности переведены. Для неверного логина 401 показывает уведомление; обновление токена и остальные ожидаемые 401 остаются тихими.

Проверки: `shared gen:api`/`build`, backend и frontend typecheck/lint/build, backend integration 40/40; unit и браузерная проверка на десктопе и 375 px. Конкретное несоответствие дат в `GET /visits/{visitId}/for-return` было исправлено отдельно.
