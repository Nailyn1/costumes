## Контекст

Deposit через soft delete.

## Критерии готовности

- [x] `unissue` помечает текущий Deposit `deletedAt`, сохраняя исходную запись и её сумму/тип.
- [x] Повторная выдача создаёт новый активный Deposit того же визита, не затрагивая историю.
- [x] Выборки и операции возврата используют только активный Deposit (`deletedAt: null`).
- [x] Unit и integration тесты покрывают выдачу → отмену → повторную выдачу и отсутствие старого залога в активных ответах.
- [x] Новая миграция Prisma безопасна для существующих данных; typecheck, lint, unit и integration проходят.

## План

1. Убрать глобальную уникальность `deposits.visit_id`, сохранить уникальность только активной строки и перевести связь визита с залогом на историю.
2. Обновить выдачу, отмену, возврат и выборки на активный залог.
3. Добавить регрессионные unit/integration тесты, создать миграцию и проверить её SQL.

## Результат

Миграция `20261018180247_deposit_soft_delete` удаляет глобальный уникальный индекс `visit_id` и добавляет частичный уникальный индекс для активных записей (`deleted_at IS NULL`). Существующие данные ему соответствуют, поскольку прежний индекс уже гарантировал уникальность всех строк. `unissue` ставит `deletedAt`; повторная выдача создаёт новую запись. Все активные выборки и операции возврата фильтруют историю. Integration проверяет две записи залога после повторной выдачи, правильный активный залог в ответе и отсутствие старого в списке к возврату.
