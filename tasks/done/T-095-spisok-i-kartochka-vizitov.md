# T-095 · Все визиты: поиск, карточка, история

- **Приоритет:** на согласование владельцем
- **Область:** Фичи
- **Создана:** 2026-10-22
- **Завершена:** 2026-10-22
- **Статус:** Выполнена

## Контекст

Выдача ищет reserved, возврат — issued. Нет места найти завершённый/отменённый визит и увидеть весь цикл. Это отдельная часть исходной T-033.

[Исследование](../research/2026-10-22-visits-quick-issue-history.md), §§1–2, 5–6, 8–9. Зависимости: T-094 (история), T-098 (version для будущих действий). Редактор — T-033, дополнительная выдача — T-096.

## Критерии готовности

- [x] `/bookings/visits` в меню и `/bookings/visits/:id`; прямой URL работает после обновления страницы.
- [x] Поиск по visitCode/клиенту/телефону/ребёнку/костюму/inventoryCode; фильтры статуса и обеих дат, серверная пагинация и стабильная сортировка `createdAt DESC, id DESC` (endpoint не обещает ранжирование совпадений).
- [x] Доступны reserved/issued/completed/cancelled без изменения смысла существующих endpoints рабочих очередей.
- [x] API карточки содержит orderId/childId/costumeId и version для будущего редактора; UI не показывает внутренние ID/version. Бирки используют текущие статусы; `not_required` подключается задачей T-036.
- [x] Для reserved показаны суммы брони без вызова запрещённого для него balance; после выдачи — фактический баланс, без повторного finalPayment.
- [x] Действия соответствуют статусу и используют текущие команды; нет обхода серверных ограничений.
- [x] Cancelled история заканчивается отменой; старые визиты показывают ограничение доступной истории.
- [x] Десктопная таблица и мобильные карточки 375px, loading/error/empty; ссылки из выдачи/возврата ведут в карточку.
- [x] Frontend и backend-проверки поиска, пагинации, статусов, soft-delete, истории; DoD.

## План

1. Один backend/shared-владелец определяет `GET /visits` и `GET /visits/:id`, DTO detail с идентификаторами и финансовыми полями; статические routes раньше :id.
2. Реализовать read API с переиспользованием утилит поиска/ранжирования, без загрузки всех визитов в браузер.
3. UI-агент создаёт новые pages/components/hooks/services, использует shared и API истории T-094.
4. Интегратор добавляет routes/menu и проверяет query invalidation старых ключей `["visit", ...]` и `["visits", ...]`; не полагаться на один несовпадающий префикс.
5. Проверить отменённые, старые, долг после completed и незакрытый залог, затем общий DoD.

## Результат

Добавлены shared-контракты и read API списка/карточки визита, новые страницы поиска и detail, ссылки из рабочих очередей, история действий и действия текущих команд. История импортированных платежей помечается отдельно, UI не показывает timestamp миграции как дату оплаты. `not_required` не добавлялся и остаётся в зависимости T-036.

Проверки: `pnpm test` — backend 26 suites, 351 passed + 1 todo; frontend 19 files, 158 passed + 1 todo. `pnpm test:int` — 12 suites, 54 passed. Дополнительно прошли shared build, backend typecheck, frontend `tsc -b`, frontend full lint и ESLint всех изменённых backend T-095 файлов. Общий backend lint оставляет 5 существующих Prettier errors в `redis.idempotency.spec.ts` и `redis.idempotency.ts`; изменённые файлы T-095 проходят ESLint. Desktop и 375px browser QA прошли для поиска, фильтра статуса, прямого URL/перезагрузки, отмены с причиной/автором, возврата залога и расчёта долга с обновлением истории.
