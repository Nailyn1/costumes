# T-092 · Явные доменные правила визита

- **Приоритет:** medium — после T-028
- **Область:** Архитектура backend

- **Выполнена:** 2026-10-21

## Контекст

Бизнес-правила бронирования, выдачи, отмены и возврата сосредоточены в `apps/backend/src/visit-order/visit-order.service.ts` (около 1400 строк) вместе с запросами Prisma и формированием API-ответов. Из-за этого границы правил трудно увидеть и тестировать отдельно. Записи Prisma являются состоянием хранения, а не доменными объектами; оборачивать каждый Client/Costume/Visit/Order в класс без поведения не даст пользы.

Первый кандидат на явную границу — визит как единая операция над заказами, платежами и залогом. T-028 завершена: фактические платежи хранятся в `VisitMoneyOperation`, а расчёт вынесен в чистый `domain/visit-balance.ts`. Это действующая часть будущей доменной модели, которую не следует переписывать заново.

## Критерии готовности

- [x] Решение о следующей границе (Client, Costume или Notification) принято по обнаруженному дублированию логики, а не по требованию «все сущности должны стать классами».

## Результат

Добавлен чистый класс `Visit` в `domain/visit.ts`: правила создания, выдачи, отмены выдачи, завершения возврата, отмены брони и позднего расчёта возвращают решения без обращения к БД. Сервис явно собирает снимок, применяет решение в прежних транзакциях и переводит стабильные коды доменных ошибок в прежние русские HTTP-сообщения. `visit-balance.ts` из T-028 переиспользуется без изменения формулы; активность платежа передаётся в снимке отдельным флагом. Залог по-прежнему ведётся отдельно: отмена выдачи возвращает решение о soft delete залога, а его возврат не блокирует завершение визита.

Новые прямые unit-тесты домена дополнили существующие: всего 302 unit-теста и 40 integration-тестов прошли. Backend typecheck, lint и `git diff --check` прошли. Публичный API и схема БД не менялись. Новые классы Client/Costume/Notification пока не вводятся: подтверждённого повторения их доменных правил в этом рефакторинге не обнаружено.

## Реализованная граница

`Visit` — агрегат одной брони: статус визита, активные заказы и финансовое состояние после T-028. Вход домена — отдельный тип-снимок с примитивами (`VisitStatus`, `OrderStatus`, целые суммы и флаг отмены платежа), без Prisma-моделей и API DTO. Период проверяется при создании, а даты заказов копируются из визита. Загрузка снимка и сохранение решения остаются в сервисе. Классы `Client`, `Costume` и `Order` ради обёртки записей не создаются.

Методы `issue`, `unissue`, `completeReturn`, `cancel` возвращают решение: следующий статус визита и заказов, денежную операцию или её отмену, дополнение к заметке. `unissue` также предписывает soft delete активного залога. Создание и возврат залога остаются в сервисе, отдельно от баланса аренды. Решение вычисляется без записи в БД; сервис применяет его атомарно в транзакции. Ошибки домена имеют стабильный код, который сервис переводит в существующие русские HTTP-сообщения. Публичный контракт и схема БД не менялись.

Проверки домена: выдача только `reserved` и целиком; отмена выдачи только `issued`; завершение только `issued`, когда все активные заказы выданы; отмена брони только `reserved`; залог не блокирует завершение; дата начала не позже возврата; предоплата каждого заказа не превышает аренду. Даты заказов сервис копирует из визита при создании, поэтому они совпадают по построению. Отсутствующие/удалённые записи и занятость костюмов остаются ответственностью сервиса и запросов к БД. Денежный баланс и действия по оплате берутся из модели T-028, а не из `Order.finalPayment`.

Рефакторинг подключён к созданию, выдаче, отмене выдачи, возврату, позднему расчёту и отмене брони. Контроллеры и Prisma-схема не менялись.
