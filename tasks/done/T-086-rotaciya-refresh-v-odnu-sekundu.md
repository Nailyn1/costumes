# T-086 · Ротация refresh-токена при быстром повторном выпуске

- **Приоритет:** high
- **Область:** Баги домена
- **Создана:** 2026-10-18
- **Выполнена:** 2026-10-18

## Контекст

`AuthService.issueTokens` подписывает refresh JWT только с payload `{id, login}` и фиксированным сроком `7d`. Два выпуска в течение одной секунды дают побайтно одинаковый JWT (подтверждено через `JwtService.sign`), потому что `iat` имеет секундную точность. При `POST /auth/refresh` новый токен тогда совпадает со старым, а ротация не отзывает старый cookie.

## Критерии готовности

- [x] Каждый успешный refresh выпускает новый, отличный от старого токен даже в ту же секунду.
- [x] Сразу после refresh старый cookie возвращает 401, новый работает.
- [x] Redis-ключ `rf:{userId}` сохраняет только актуальный токен с TTL 7 дней.
- [x] Unit и integration тесты доказывают ротацию без задержек по времени.

## План

1. Добавить регрессионный unit-тест с фиксированным временем и настоящей подписью JWT, а также HTTP integration-сценарий для старого и нового cookie и Redis TTL.
2. Добавить уникальный идентификатор в каждый refresh JWT, не меняя payload access JWT и API-контракт.
3. Запустить unit, typecheck и lint; integration прогонит основной агент последовательно с другими наборами.

## Результат

В refresh JWT добавляется случайный `jti`; payload access JWT и API-контракт не изменились. Регрессионный unit-тест с фиксированной секундой сначала воспроизвёл совпадение токенов, затем прошёл после исправления. Добавлен integration-сценарий HTTP cookie и проверки значения/TTL в Redis.

Локально пройдены: `auth.service.spec.ts` (9 тестов, 1 существующий todo T-085), backend typecheck и lint изменённых файлов. Основной агент последовательно запустил весь backend integration-набор: 33/33 прошли, включая регрессию ротации.
