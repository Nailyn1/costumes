# T-096 · Добавить и сразу выдать костюм в выданном визите

- **Приоритет:** согласовано владельцем
- **Область:** Фичи
- **Создана:** 2026-10-22
- **Выполнена:** 2026-10-23

## Контекст

Клиент уже получил костюм и возвращается за ещё одним на те же даты. Нельзя повторять visitIssue для всего визита или отменять прежнюю выдачу ради добавления строки. При другой дате возврата владелец подтвердил отдельный визит.

[Исследование](../research/2026-10-22-visits-quick-issue-history.md), §§3, 5, 7–9. Основа: T-094/T-098, T-095 и T-036 выполнены. Изменения очереди и отправок WhatsApp (T-100/T-101) отложены владельцем и не блокируют эту задачу.

## Решения владельца от 2026-10-22

- При добавлении костюма действующий залог сохраняется без изменения (тип, сумма, статус). Дополнительный залог сейчас не вводится.
- Старые выданные заказы не редактируются: замена/удаление/изменение цены пока вне работы. Добавить и сразу выдать новый заказ — отдельная команда этой задачи.
- Визит и его код сохраняются; при других датах возврата создаётся отдельный визит. WhatsApp автоматически не отправляется; прежнее сообщение не обновляется, код остаётся действительным. Ручная отправка — будущая T-101.
- Итоговый план утверждён владельцем: реализация разрешена после T-036/T-033 несколькими агентами в одном дереве, отдельный коммит на задачу, без push. Поиск совпадающих визитов и изменения очереди WhatsApp в волну не входят.

## Критерии готовности

- [x] В карточке issued есть действие «Добавить и выдать»; можно выбрать ребёнка клиента или создать inline, несколько костюмов одному ребёнку разрешены.
- [x] Клиент и обе даты наследуются; прежние заказы, их платежи и действующий залог сохраняются.
- [x] Новые Orders получают `issued/not_required`; в ledger отражена только фактически полученная сейчас сумма, без изменения старых платежей/залога.
- [x] Баланс всего визита учитывает старый долг/переплату, новые суммы и платежи без двойного счёта.
- [x] Одна транзакция с version/CAS, проверкой доступности, audit и receipt; сбой откатывает все изменения.
- [x] Повтор команды не дублирует дополнение, в том числе после очистки Redis; гонки с возвратом и unissue сериализуются.
- [x] Все активные заказы видны при возврате; новые отсутствуют в незаписанных; автоматических WhatsApp-отправок нет.
- [x] Полный unissue аннулирует выдачные issue_payment, снимает залог, сбрасывает оплаты; написанные бирки сохраняются, новые `not_required` возвращаются в `not_written`.
- [x] Действие не редактирует/не удаляет уже выданные старые заказы; ограничение описано в правилах домена.
- [x] Unit/integration/frontend-тесты и применимые lint/TypeScript-проверки прошли. Ручная браузерная проверка и 375 px остаются владельцу по [чек-листу](../research/2026-10-23-visit-manual-qa.md), не отмечены выполненными.

## План

1. Закрыть бизнес-вопросы, контракт `POST /visits/:id/add-and-issue` через shared.
2. Чистое доменное решение дополнения, сервис с tx и общей защитой T-098; не вызывать повторно публичный visitIssue.
3. UI на общих Order/Issue полях с итогами по всему визиту; сохранение формы при конфликте.
4. Тесты и E2E: исходная выдача → дополнение → возврат; отдельно полный unissue → повторная выдача. Обновление документации.
