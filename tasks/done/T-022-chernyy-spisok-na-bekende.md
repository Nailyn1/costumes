# T-022 · Чёрный список на бэкенде

- **Приоритет:** high — до сезона обязательно
- **Область:** Баги домена (подтверждены владельцем, см. domain.md §6)
- **Создана:** 2026-10-15
- **Выполнена:** 2026-10-15

## Контекст

`createVisit` должен отклонять клиента с `isBlacklisted=true` (сейчас блок только в UI).

## Критерии готовности

- [x] `createVisit` отклоняет клиента с `isBlacklisted = true`; проверка внутри транзакции, где клиент уже читается.
- [x] Текст на русском: имя клиента, причина из `blacklistReason` (если есть), подсказка снять запрет на странице «Клиенты».
- [x] Фронт показывает сообщение пользователю (меняется ли фронт — см. «Результат»).
- [x] Unit-тесты: с причиной и без причины.

## Результат

В `createVisit` (`apps/backend/src/visit-order/visit-order.sevice.ts`) сразу после чтения клиента в транзакции добавлена проверка `client.isBlacklisted` → `BadRequestException` вида «Клиент «Имя» в чёрном списке — бронирование невозможно. Причина: …. Чтобы забронировать, снимите запрет на странице «Клиенты».» (фрагмент «Причина» — только если `blacklistReason` задана). Ничего не записывается: исключение вылетает до `visit.create`.

**Почему `BadRequestException` (400), а не `Forbidden` (403):** все сотрудники равны и ролей нет — это не вопрос прав доступа пользователя, а нарушение бизнес-правила над данными клиента, как и остальные отказы `createVisit` (занятый костюм, предоплата > аренды), которые уже 400. 403 в клиенте нигде специально не обрабатывается, но для единообразия выбран 400.

**Фронт не менялся:** глобальный `MutationCache.onError` → `handleError` берёт `error.response.data.message` и показывает красный toast «Operation error»; Nest-исключение отдаёт `message` как строку.

Побочное наблюдение: проверка стоит после проверок кода/занятости костюмов, поэтому при одновременно занятом костюме и клиенте из ЧС пользователь сначала увидит ошибку про костюм — не критично. Из `domain.md` §6 убран пункт про чёрный список. Добавлены unit-тесты (2 шт.).
