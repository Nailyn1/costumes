# T-098 · Конкуренция визитов и безопасные повторы выдачи

- **Приоритет:** на согласование владельцем
- **Область:** Баги домена / Фичи
- **Создана:** 2026-10-22

## Контекст

`isSuitAvailability` читает отсутствие пересечений перед созданием, но createVisit использует транзакцию с изоляцией по умолчанию. Код не содержит отдельного ограничения пересекающихся заказов в БД. Две конкурентные транзакции могут обе пройти проверку. Это риск, установленный по коду, без воспроизведения на живой БД.

Редактирование и дополнительная выдача требуют защиты от устаревших форм. Redis-кэш идемпотентности живёт 24 часа и записывается после коммита; новый вызов Axios получает новый ключ, поэтому повтор команды после потери ответа нельзя считать решённым автоматически.

[Исследование](../research/2026-10-22-visits-quick-issue-history.md), §§2, 7–10. Зависимость последовательной работы: T-094, т.к. меняются одни сервисы/Prisma/shared. Фундамент T-036/T-033/T-096.

## Критерии готовности

- [x] Integration-тест двух конкурентных обычных броней на один костюм через управляемый барьер, без sleep: один успех, вторая транзакция повторно проверяет доступность; в БД остаётся одна бронь.
- [x] Общий runner использует Serializable и ограниченный повтор полного callback при Prisma P2034 и PostgreSQL SQLSTATE 40001; после лимита service/receipt helper возвращают понятный 409. Детерминированные integration-тесты issue/cancel и return/unissue проверяют согласованность Visit/Order, единственный согласованный набор платежа/залога/audit-событий; receipt integration проверяет rollback при невалидном результате и ошибке записи audit.
- [x] `Visit.version` добавлен безопасной миграцией; все существующие мутации визита (выдача, отмена выдачи, отмена брони, возврат, залог, денежный расчёт, запись бирки) участвуют в CAS и увеличивают версию только при успешном изменении. Устаревшая версия в CAS отклоняется с 409. Внешний `expectedVersion` для будущих форм/команд подключается вместе с этими API в будущих задачах.
- [x] Транзакционный receipt helper хранит уникальный `commandId` и actor/path/requestHash/result: совпадающий повтор возвращает canonical сохранённый результат; несовпадение отклоняется; P2002 разрешается чтением записи после abort исходной транзакции. Реальные DB-тесты проверяют конкурентный повтор одного receipt, отсутствие дубля платежа после очистки Redis, rollback бизнес-записи при parse/audit ошибке.
- [x] Миграция добавочная: старые визиты получают version=1 без изменения финансов; новые audit-события задним числом не создаются.
- [x] Definition of Done: unit/integration/typecheck и lint изменённых T098-файлов пройдены; миграция проверена; доменные правила обновлены.

### Отложено до появления команд и форм

- [ ] Будущие edit, append/return и append/unissue команды, их формы и сквозные повторы с тем же `commandId` (включая 401/неизвестный исход) подключить в T-033/T-036/T-096. Существующие issue/cancel и return/unissue проверяются в этой задаче integration-гонками.
- [ ] API и UI для quick/add-and-issue, включая создание/повтор `commandId`, связывание платежа с receipt и применение внешнего `expectedVersion`, реализовать в T-036/T-096 через shared и frontend.
- [ ] Значение `not_required` и сквозная проверка быстрой выдачи — T-036; эту задачу не включать.

## План

1. Безопасно добавить version и command receipt, проверить SQL миграции и сгенерировать Prisma-клиент.
2. Подключить общий Serializable retry и CAS ко всем текущим мутациям визита; повторять только DB work и держать actor/command id/payload snapshot вне повторяемого callback.
3. Добавить receipt helper для будущих денежных команд, включая разрешение конфликта unique после неуспешной транзакции через чтение сохранённой записи.
4. Детерминированно проверить конкурентные брони и rollback состояния вместе с audit событиями; интеграционные наборы запускать только при свободном lease.
5. Обновить доменные гарантии и явно оставить проверки отсутствующих edit/append/quick flows в будущих задачах. Уникальность «клиент + даты» не вводить без отдельного решения и проверки старых дублей.

## Результат

Выполнена 2026-10-22. Добавлены version/CAS, безопасная миграция, bounded Serializable retry для P2034/SQLSTATE 40001/40P01 и транзакционный command receipt helper. Проверены детерминированные гонки брони, issue/cancel и return/unissue; реальные DB-проверки receipt concurrency, replay после Redis loss и rollback parse/audit errors. Будущие edit/append/quick endpoints/forms, внешний `expectedVersion` и frontend-командные повторы остаются в T-033/T-036/T-096.

Проверки: `pnpm test` — backend 351 passed, 1 todo; frontend 158 passed, 1 todo. `pnpm test:int` — 11 suites, 50 passed. Backend typecheck и targeted ESLint по изменённым T098-файлам прошли.
