# T-102 · Явно ограничить поля Order при обычном создании брони

- **Приоритет:** на согласование владельцем
- **Область:** Баги домена
- **Создана:** 2026-10-22

## Контекст

При ревью T-036 найдено по коду: обычный `VisitOrderService.createVisit` передаёт `...o` из запроса в Prisma nested `orders.create`. Generated Zod-схемы сохраняют незнакомые поля (`catchall`), поэтому дополнительные Prisma-поля заказа (например, `status`, `tagStatus`, `deletedAt`, `finalPayment`) могут попасть в запись в обход полей API. Факт установлен чтением кода; отдельное HTTP-воспроизведение для обычной брони пока не проводилось.

В новой быстрой выдаче T-036 применяется явный список разрешённых полей. Обычный create не исправляется заодно: отдельная задача по правилам проекта.

## Критерии готовности

- [ ] Integration-тест воспроизводит влияние дополнительных полей обычного `POST /visits` на старом коде, без реальных уведомлений.
- [ ] Prisma получает только явные разрешённые поля Order; статусы, даты, связи и внутренние финансовые поля задаёт сервер.
- [ ] Не нарушена совместимость API с незнакомыми полями: они не становятся записываемыми полями БД.
- [ ] Обычная бронь, предоплата, бирки и история проходят регрессионные проверки; DoD.

## Результат

Записано при ревью. Реализация не начата и не входит в согласованную волну T-036/T-033/T-096.
