# T-093 · Единый формат ошибок API и понятные сообщения на фронте

- **Приоритет:** high — до сезона обязательно
- **Область:** Баги домена / API / UX
- **Создана:** 2026-10-21

## Контекст

При нарушении контракта ответа API `typed-openapi` выбрасывает ошибку Zod, а глобальный обработчик фронта показывает её `error.message` целиком. Сотрудник видит технический JSON с `invalid_format`, регулярными выражениями и путями полей (пример: даты в карточке возврата T-028). Даже если конкретное несоответствие контракта исправлено, такой же экран возможен при следующей ошибке ответа.

Сейчас `apps/crm-frontend/src/utils/handleError.ts` возвращает сырое `Error.message`, а `apps/crm-frontend/src/app/queryClient.ts` показывает английские заголовки `Data upload error` и `Operation error`. На backend `apps/backend/src/common/pipes/zod-validation.pipe.ts` возвращает `Validation failed` и вложенное дерево `errors`; `apps/backend/src/common/filters/prisma-client-exception.filter.ts` обрабатывает только часть ошибок Prisma. Нужно определить один предсказуемый формат ошибок API и не показывать сотруднику внутренние диагностические данные.

## Критерии готовности

- [ ] Определён и описан в `.agents/shared-api.md` единый формат ошибочного ответа API: код/статус, короткое русское сообщение для сотрудника и, где полезно, ошибки конкретных полей. Сохранена совместимость с `typed-openapi` и статусами, уже описанными в TypeSpec.
- [ ] Валидация входных данных, Nest-исключения и известные ошибки Prisma отдают этот формат; неожиданные ошибки не раскрывают внутренние детали клиенту и остаются доступными в серверных логах/Sentry.
- [ ] Проведён аудит контроллеров и сервисов: убраны сырые сообщения библиотек и неоднородные тела ошибок там, где они попадают в интерфейс. Доменные причины ошибок остаются конкретными и на русском.
- [ ] Фронт централизованно различает ожидаемую ошибку API, ошибку сети и нарушение контракта запроса/ответа. Для нарушения контракта показывает короткое русское сообщение и оставляет детали в консоли/Sentry; заголовки уведомлений на русском.
- [ ] Отдельные поля формы получают понятную ошибку, если backend её прислал; существующее подавление ожидаемых 401 и обновление токена работают как прежде.
- [ ] Есть тесты backend и frontend для 400/409/500, ошибок полей, сетевого сбоя и Zod-ошибки ответа. Ни один из них не выводит пользователю JSON, regex или stack trace.

## План

1. Согласовать форму error response в `shared/api-spec/` и обновить генерацию/экспорты `shared/src/`.
2. Реализовать общую нормализацию ошибок backend на HTTP-границе; адаптировать Zod pipe и Prisma filter. Проверить существующие исключения в `apps/backend/src/`.
3. Обновить `apps/crm-frontend/src/utils/handleError.ts` и `src/app/queryClient.ts`; проверить локальные обработчики форм, которые обходят общий обработчик.
4. Добавить сквозные тесты на реальные ошибочные ответы и на несовпадение успешного ответа с контрактом.

## Принятые решения для реализации

- Сохраняем совместимые обязательные поля существующего `Common.Error`: `statusCode: number` и `message: string`. Дополнительные машинный `code` и ошибки полей (`fieldErrors`) — необязательные; поле `error` остаётся совместимым на время перехода. Точную запись этих типов сначала проверяем генерацией TypeSpec/OpenAPI/typed-openapi, не правим generated-файлы вручную.
- Для ожидаемых 4xx backend возвращает короткое русское `message` с конкретной причиной и прежний HTTP-статус. Для неожиданного 500 клиент получает общее русское сообщение; подробности остаются в серверном логе/Sentry без вывода секретов и персональных данных в ответ.
- Единая нормализация на HTTP-границе Nest покрывает Nest-исключения, Zod validation и известные ошибки Prisma. Существующий `PrismaClientExceptionFilter` нужно встроить в эту схему без двойной обработки. Не переписывать каждый контроллер только ради одинаковой оболочки ответа; сервисы сохраняют конкретные доменные причины.
- Frontend различает `TypedStatusError`/Axios с корректным ответом API, сетевую ошибку и `ZodError` при проверке запроса либо ответа. Сотруднику показываются короткие русские сообщения; детали Zod доступны разработчику в console/Sentry. Не выводить `Error.message` произвольного исключения без проверки: он может содержать JSON, regex или stack trace.
- Сохраняем обновление токена и подавление ожидаемых 401. Не создаём второй toast в локальном обработчике, если ошибку уже показывает глобальный `QueryClient`. Поле формы подсвечиваем только там, где есть соответствующий `fieldErrors`.
- Порядок делегирования: сначала один исполнитель закрепляет и генерирует контракт `shared`, затем backend и frontend можно делать параллельно. T-092 завершена; `visit-order.service.ts` теперь переводит доменные ошибки в HTTP и входит в аудит сообщений T-093. Финальная сквозная проверка и аудит остаются у принимающего агента.

## Результат

Ожидает выполнения. Конкретное несоответствие дат в `GET /visits/{visitId}/for-return` уже исправлено отдельно; эта задача защищает интерфейс от показа технических ошибок при других сбоях.
