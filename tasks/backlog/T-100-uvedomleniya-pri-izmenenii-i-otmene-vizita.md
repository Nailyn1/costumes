# T-100 · Согласовать WhatsApp с изменением и отменой визита

- **Приоритет:** на согласование владельцем
- **Область:** Баги домена / Фичи
- **Создана:** 2026-10-22

## Контекст

**Решение владельца 2026-10-22:** задачу отложить целиком, существующую очередь в текущей волне не менять. T-100 не блокирует T-033/T-036/T-096. Ранее найденные ограничения сохраняются в backlog; не добавлять проверки/подавление pending, снимки, retry-политику или resend в рамках редактора.

`notification.repository.ts:findForSending` загружает все Orders без deletedAt-фильтра, а `processWhatsAppSending` строит сообщение по текущему визиту, без проверки статуса отменённого визита. Поведение очереди и повторной отправки остаётся отдельной связанной задачей. По решению владельца её согласование не блокирует T-033.

[Исследование](../research/2026-10-22-visits-quick-issue-history.md), §§2–3, 5, 9. Владелец 2026-10-22 подтвердил: изменение визита не отправляет WhatsApp автоматически; уже отправленное сообщение остаётся прежним, ID/код визита сохраняются. Новую кнопку ручной отправки пока не делать — отдельная T-101.

Эта задача остаётся про безопасность существующей очереди. Поведение уже ожидающего сообщения при edit/cancel ещё нужно согласовать: последнее решение не означает ни автоматическую отмену pending job, ни разрешение отправлять подтверждение отменённого визита. Реализация — после повторного утверждения плана.

## Критерии готовности

- [ ] Тестом зафиксированы чтение soft-deleted Orders и отправка после отмены; исправляется только согласованная политика.
- [ ] Сообщение не содержит удалённых заказов; поведение soft-deleted Client/Child/Costume/Visit обработано по правилам проекта.
- [ ] Зафиксировано: сообщение — снимок подтверждения или актуальные данные на момент отправки; редактирование не меняет смысл уже отправленного текста в истории.
- [ ] Pending job после edit/cancel, retry и ручной resend имеют явные разрешения; быстрый режим не создаёт сообщений.
- [ ] Если вводятся superseded/suppressed состояния, они не подменяют Green-API delivery status и отражены в shared/UI; нельзя молча переиспользовать failed.
- [ ] Есть тесты гонки отправки с изменением/отменой и описан предел гарантии: уже ушедший запрос провайдеру нельзя отозвать транзакцией БД.
- [ ] Никаких реальных Green-API в тестах; DoD и документация.

## План

1. Согласовать продуктовую политику и минимальный контракт; отдельно выбрать хранение снимка отправленного текста/получателя и связь с версией визита.
2. Воспроизводящие тесты, новые миграции/TypeSpec только при необходимости.
3. Исправить выборку активного состава и проверки перед отправкой в рамках согласованной политики; не добавлять автоматическое уведомление из PATCH и новую кнопку manual resend (T-101).
4. Проверить очередь и историю сообщений на старых и отредактированных визитах. Реализация T-033 не зависит от завершения этой отложенной задачи.

## Результат

Найдено по коду; продуктовая политика и исправление ещё не выполнены.
