# T-092 · Явные доменные правила визита

- **Приоритет:** medium — после T-028
- **Область:** Архитектура backend
- **Создана:** 2026-10-20

## Контекст

Бизнес-правила бронирования, выдачи, отмены и возврата сосредоточены в `apps/backend/src/visit-order/visit-order.service.ts` (около 1400 строк) вместе с запросами Prisma и формированием API-ответов. Из-за этого границы правил трудно увидеть и тестировать отдельно. Записи Prisma являются состоянием хранения, а не доменными объектами; оборачивать каждый Client/Costume/Visit/Order в класс без поведения не даст пользы.

Первый кандидат на явную границу — визит как единая операция над заказами, платежами и залогом. T-028 завершена: фактические платежи хранятся в `VisitMoneyOperation`, а расчёт вынесен в чистый `domain/visit-balance.ts`. Это действующая часть будущей доменной модели, которую не следует переписывать заново.

## Критерии готовности

- [ ] Чистые доменные правила визита живут в `apps/backend/src/visit-order/domain/`, не импортируют NestJS, Prisma, HTTP DTO или UI.
- [ ] Правила переходов `reserved → issued → completed`, отмены выдачи, расчётов и проверки всех заказов представлены методами/функциями с явными входами и результатами.
- [ ] `VisitOrderService` остаётся координатором загрузки, транзакций, сохранения и перевода доменных ошибок в HTTP-ошибки.
- [ ] Поведение API и схема БД не меняются только ради рефакторинга; существующие integration-сценарии остаются зелёными.
- [ ] Новые unit-тесты покрывают доменные правила напрямую, а не повторяют устройство класса.
- [ ] Решение о следующей границе (Client, Costume или Notification) принято по обнаруженному дублированию логики, а не по требованию «все сущности должны стать классами».

## Предлагаемая граница

`Visit` — агрегат одной брони: статус визита, активные заказы, общие даты и финансовое состояние после T-028. Вход домена — отдельный тип-снимок с примитивами (`VisitStatus`, `OrderStatus`, целые суммы, даты), без Prisma-моделей и API DTO. Загрузка снимка и сохранение решения остаются в сервисе. Не создавать классы `Client`, `Costume` и `Order` только ради обёртки записей.

Методы `issue`, `unissue`, `completeReturn`, `cancel` возвращают решение: следующий статус визита и заказов, действие над залогом/денежной операцией, дополнение к заметке. Решение вычисляется без записи в БД; сервис применяет его атомарно в транзакции. Ошибки домена имеют стабильный код, который сервис переводит в существующие русские HTTP-сообщения. Публичный контракт и схема БД не меняются ради этого рефакторинга.

Проверки домена: выдача только `reserved` и целиком; отмена выдачи только `issued`; завершение только `issued`, когда все активные заказы выданы; отмена брони только `reserved`; залог не блокирует завершение; даты всех заказов совпадают с датами визита; предоплата каждого заказа не превышает аренду. Отсутствующие/удалённые записи и занятость костюмов остаются ответственностью сервиса и запросов к БД. Денежный баланс и действия по оплате брать из модели T-028, а не из `Order.finalPayment` текущей реализации.

Последовательность: завершить T-028 и его тесты → написать прямые unit-тесты переходов/баланса → подключать доменную модель к одному сценарию сервиса за раз (`cancel`, `unissue`, `completeReturn`, `issue`, создание) → прогнать существующие integration-тесты после каждого этапа. Первым коммитом можно вынести только переходы, без одновременного переустройства контроллеров и Prisma-схемы.
