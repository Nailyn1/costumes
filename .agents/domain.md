# Домен: прокат детских костюмов

Внутренняя CRM одной точки проката. Пользователи — сотрудники точки (несколько аккаунтов, ролей нет, все равны). Работают с ПК и с телефона — **любой экран должен быть удобен на мобильном**. Сезон — новогодние праздники; за прошлый сезон через систему прошло ~500 аренд. Валюта — тенге (₸), суммы хранятся целыми числами. Клиенты — из Казахстана, телефоны `+7...`.

Источник UX-замысла — canvas владельца в Obsidian (зелёные карточки = UX-флоу). Этот файл — его выжимка, сверенная с кодом.

## 1. Сущности

| Сущность | Смысл | Ключевые поля |
|---|---|---|
| **User** | Сотрудник. Создаётся только через seed. | `login`, `password` (argon2id), `name` |
| **Client** | Взрослый, который берёт и оплачивает аренду. | `name`, `phone`, `notes`, `isBlacklisted`, `blacklistReason`, `deletedAt` |
| **Child** | Ребёнок клиента, на которого берётся костюм. | `clientId`, `name`, `deletedAt` |
| **Costume** | Физическая единица инвентаря (один пакет). | `inventoryCode` (`C-0001`, генерирует БД), `name`, `notes`, `deletedAt` |
| **CostumePhoto** | Фото костюма (T-111): несколько на костюм, первое по `sortOrder` — обложка. Файлы лежат в S3, в БД только ключи. | `costumeId`, `key`, `thumbKey`, `width`, `height`, `sizeBytes`, `sortOrder`, `createdByUserId`, `deletedAt` |
| **Visit** | Одна «поездка» клиента: одна дата выдачи, одна дата возврата. Группирует заказы. | `visitCode` (4 цифры), `clientId`, `startDateTime`, `endDateTime`, `issueTimeFrom`, `issueTimeTo`, `returnTimeUntil`, `status`, `notes` |
| **Order** | Один заказ = **один ребёнок + один костюм + один период аренды**. Деньги живут здесь. | `visitId`, `clientId`, `childId`, `costumeId`, `startDateTime`, `endDateTime`, `rentPrice`, `prepaymentAmount`, `finalPayment`, `tagStatus`, `status`, `notes` |
| **Deposit** | Залог выдачи: у визита один активный, прошлые записи сохраняются после отмены выдачи. | `type: document \| cash \| none`, `amount` (только для cash), `returned`, `deletedAt` |
| **VisitMoneyOperation** | Фактическое движение денег за аренду визита, отдельно от залога. | `kind: issue_payment \| debt_payment \| customer_refund`, положительная `amount`, `voidedAt`, `legacyImported` |
| **Notification** | WhatsApp-сообщение клиенту о брони. | `visitId`, `type` (`booking_confirmation`), `status`, `externalId` (id в Green-API), `traceId`, `errorText` |

**Фото костюма.** До 15 активных фото на костюм (16-е → 409). Загрузка — `POST /costumes/:id/photos` (multipart: `image` ≤ 2 МБ, `thumb` ≤ 200 КБ, только JPEG/WebP, тип проверяется по сигнатуре файла, плюс текстовые поля `width`/`height`), список — `GET`, порядок — `PATCH /costumes/:id/photos/order` (все id активных фото; первое — обложка), удаление — `DELETE …/:photoId` (soft delete, объекты из S3 удаляются после него; ошибка S3 только логируется). В ответах костюмов (поиск, список, занятость) и заказов (бирки, выдача, возврат, карточка визита) приходят `coverThumbUrl?` и `photoCount` без полного списка. Подробности хранения — [architecture.md](./architecture.md#s3-фото-костюмов).

Статус костюма в ответе API вычисляется по активным заказам; отдельной хранимой колонки `Costume.status` нет. Занятость на период определяется пересечением дат заказов.

Связи: `Client 1→N Child`, `Client 1→N Visit`, `Visit 1→N Order`, `Visit 1→N Deposit` (в истории, не более одного активного), `Visit 1→N Notification`, `Costume 1→N Order` (во времени).

Вычисляемые (не хранятся): `remaining = rentPrice − prepaymentAmount` по заказу; `totalRent / totalPrepayment / totalRemaining` визита — суммы по заказам.
Баланс визита: `аренда − предоплата − активные поступления + активные возвраты клиенту`. Положительное значение — долг, отрицательное — переплата к возврату. Фактические деньги берутся из `VisitMoneyOperation`; `Order.finalPayment` остаётся историческим распределением и повторно в баланс не суммируется. Залог в баланс аренды не входит. Старые доплаты при миграции импортируются в журнал однократно; ранее потерянную переплату восстановить нельзя.

Правила переходов визита и расчётов представлены чистой моделью `apps/backend/src/visit-order/domain/visit.ts`: она принимает снимок из примитивных полей и возвращает решение, а `VisitOrderService` загружает данные и применяет решение атомарно. На выдаче проверяется статус визита `reserved`; отдельной проверки статусов заказов сейчас нет. При завершении возврата каждый активный заказ должен иметь статус `issued`.

### Коды
- `visitCode` — 4 цифры (`0000–9999`), уникален навсегда. Клиент называет его при получении. Генерируется на шаге «Проверить» и резервируется в Redis на 15 минут (`visit_code_lock:{code}`).
- `inventoryCode` — `C-` + 4 цифры из sequence `costume_code_seq` (функция `generate_costume_code()` в миграции). Пишется на физической бирке.

## 2. Статусы

**Visit:** `reserved → issued → completed`; `reserved → cancelled`.
- `reserved` — визит создан, костюмы ещё у нас.
- `issued` — все заказы выданы, костюмы у клиента, залог зафиксирован.
- `completed` — все костюмы вернули. Залог на закрытие **не влияет**.
- `cancelled` — бронь отменена (только из `reserved`).
- Откат `issued → reserved` возможен через «отмену выдачи» (`unissue`) — исправление ошибки сотрудника.

**Order:** `reserved → issued → returned`; `reserved → cancelled`. Статусы заказов меняются вместе с визитом.

**Order.tagStatus:** `not_written → written` — написана ли физическая бирка на пакет; `not_required` означает, что для быстрой выдачи бирка не нужна. При `unissue` только `not_required` сбрасывается в `not_written`, а `written` сохраняется.

**Deposit.returned:** `false → true` — вернули ли клиенту залог.

**Notification.status** (с приоритетом, статус может только расти): `failed(0) < pending(1) < sent(2) < delivered(3) < read(4) < isConfirmed(5) < noAccount(6)`.
- `isConfirmed` — клиент ответил на сообщение (любым символом) в течение 48 часов.
- `noAccount` — у номера нет WhatsApp.

## 3. Бизнес-правила (инварианты)

1. **Один визит — одна дата выдачи и одна дата возврата.** Дата и время задаются на уровне визита и копируются во все его заказы. Если клиент берёт разным детям на разные даты — это **разные визиты** (и разные сообщения).
2. В визите может быть несколько детей; у каждого заказа ровно один костюм.
3. Костюм нельзя забронировать, если у него есть пересекающийся по времени не отменённый заказ (`start < otherEnd && end > otherStart`).
4. `prepaymentAmount ≤ rentPrice` (проверяется на фронте и бэке). Предоплата обычно вносится при бронировании, но сотрудник может указать `0 ₸`, если клиент пока не может её внести.
5. **Выдача — атомарная операция над всем визитом.** Нельзя выдать часть визита, нельзя выдать повторно, нельзя редактировать заказы при выдаче. Выдавать можно только `reserved`.
6. **Возврат закрывает визит целиком**, кнопка активна только когда отмечены все костюмы. Залог не блокирует закрытие.
7. Клиент в **чёрном списке не может бронировать**. Фронт честно об этом сообщает; чтобы забронировать, сотрудник снимает запрет на странице «Клиенты».
8. **Soft delete**: клиенты, дети, костюмы, визиты, заказы и залоги не удаляются физически — только `deletedAt`. Все активные выборки фильтруют `deletedAt: null`.
9. Сотрудник должен иметь возможность исправить любую ошибку вручную (отмена выдачи, отметка залога позже, повторная отправка сообщения).
10. Телефон клиента уникален среди активных клиентов (`deletedAt IS NULL`). Номер удалённого клиента можно использовать повторно; конфликт при создании или изменении возвращает HTTP 409.
11. Доплата при выдаче может быть нулевой, частичной или больше долга: фактически полученная сумма сохраняется целиком. При отмене выдачи её запись помечается отменённой, история остаётся. При завершении возврата можно принять долг или вернуть переплату; костюмы возвращаются и при незакрытом балансе. После завершения расчёт можно закрыть отдельно, не меняя статус визита.
12. `AuditEvent` фиксирует поддержанные операции визита атомарно с изменениями. Автор HTTP-операции берётся из JWT и снимок имени — из `User`; системные действия подписываются `Система`. История читается по `occurredAt, id` по возрастанию. Визиты без событий (в том числе созданные до включения журнала) возвращают пустую историю; более ранние действия не восстанавливаются из текущего состояния.
13. `Visit.version` начинается с `1` и увеличивается при каждой успешной существующей команде, меняющей визит, заказ, деньги, залог или бирку. Запись использует compare-and-swap по прочитанной версии; команда на устаревшем снимке получает конфликт, а не перезаписывает изменение другого сотрудника. Создание визита начинает новую версию `1`.
14. Конкурирующие операции, меняющие занятость костюма, выполняются на `Serializable`; при Prisma `P2034` повторяется вся транзакция с повторной проверкой данных, ограниченное число раз. Исчерпание повторов возвращает HTTP 409. Версия отдельного визита не защищает пересечение заказов разных визитов — это обеспечивает сериализуемая проверка занятости.
15. Таблица `CommandReceipt` и helper фиксируют уникальный `commandId`, сотрудника, путь, hash запроса и результат в одной транзакции. Совпавший повтор возвращает сохранённый результат, несовпадающие actor/path/hash конфликтуют. Быстрая выдача T-036, редактирование T-033 и дополнительная выдача T-096 используют receipt.
16. Быстрая выдача создаёт визит и все заказы сразу в `issued`, с `prepaymentAmount = 0` и `tagStatus = not_required`. Время начала — фактическое местное время выдачи. «Получено сейчас» записывается один раз как `issue_payment`; сумма может быть нулевой, частичной или превышать аренду, а `finalPayment` ограничен суммой аренды. Залог отдельный, уведомление WhatsApp и очередь уведомлений не затрагиваются. Команда `/visits/quick-issue` атомарна и идемпотентна по `commandId`; после сетевой неопределённости повторяют то же тело и идентификатор.
17. Редактировать можно только `reserved` визит с активным клиентом и невыданными заказами. `PATCH /visits/:visitId` требует `commandId` и `expectedVersion`, сохраняет ID оставленных заказов, а удалённые мягко удаляет. Предоплата сохранённого заказа не меняется: цену ниже неё нельзя поставить, оплаченный заказ нельзя удалить. При добавлении нового заказа можно указать начальную предоплату (целое число от 0 до аренды, по умолчанию 0); она сохраняется в заказе и audit snapshot без дублирования в журнале доплат. При изменении дат или временных окон, ребёнка либо костюма написанная бирка сбрасывается в `not_written`; цена и заметки её не сбрасывают. Изменения, аудит и receipt фиксируются одной транзакцией; устаревшая версия даёт `409 VISIT_VERSION_CONFLICT`, успешная команда без изменений не увеличивает версию и не создаёт событие. Для поиска костюмов редактор может передать `excludeVisitId`; исключать разрешено только активную бронь.
18. T-096 добавляет костюмы только в активный `issued` визит, у которого все старые активные заказы также `issued`. Старые заказы, распределённые `finalPayment` и залог сохраняются; добавленные заказы получают тот же период и клиента, статус `issued`, `tagStatus=not_required` и нулевую предоплату. Ребёнок должен принадлежать клиенту; новый костюм не должен повторять старый или второй новый костюм и должен быть свободен на весь период. `POST /visits/:visitId/add-and-issue` требует `commandId` и `expectedVersion`; фактически полученная сумма записывается как одна операция `issue_payment`, её историческое распределение по `finalPayment` касается только новых строк и ограничено их арендой. Баланс визита считается по аренде, предоплатам и денежным операциям — `finalPayment` второй раз в нём не учитывается; залог в аренду не входит. Новые строки, версия, деньги, audit и receipt записываются атомарно; повтор той же команды возвращает прежний ответ, конфликтующие команды не оставляют частичных изменений. Команда не отправляет WhatsApp. Обычный возврат включает все заказы. Полная отмена выдачи аннулирует активные `issue_payment`, снимает активный залог, переводит заказы обратно в бронь и возвращает только бирки `not_required` в `not_written`; `written` остаются без изменений.

### Время и даты (важно!)
- Сервер работает с `process.env.TZ = 'UTC'`.
- **Местное время точки хранится как UTC «как есть»**: `2026-12-20` + `18:30` → `2026-12-20T18:30:00Z`. Никаких конвертаций часовых поясов ни на фронте, ни на бэке.
- Время окон (`issueTimeFrom`, `issueTimeTo`, `returnTimeUntil`) хранится строкой `HH:mm`.
- Даты в API — строки `YYYY-MM-DD`.

## 4. UX-флоу (страницы)

Маршруты фронта: `src/app/router.tsx`. Все страницы, кроме `/login`, — за `PrivateRoute` + `MainLayout`.

### 4.1 Бронирование — `/bookings/new` (`CreateBookingPage`)
Одна форма, один экран, без переходов; все сущности добавляются **inline через `+`**.
1. **Клиент:** live-поиск по имени/телефону (в выпадашке — имя, телефон, дети). `+` — inline-создание (имя + телефон с маской `+7 (___) ___ __ __`), после создания клиент выбирается автоматически. Клиент из чёрного списка в поиске недоступен для выбора.
2. **Дата и время визита:** умный ввод даты (`11` → `11.MM`, отображается «11 декабря»). Время подставляется автоматически:
   - будни: выдача `18:30–19:30`, вернуть до `18:00`;
   - выходные (сб/вс): выдача `10:00–19:00`, вернуть до `19:00`;
   - «Изменить» раскрывает ручной ввод, применяется ко всем заказам.
3. **Блок «Ребёнок + костюм + финансы»** (повторяемый):
   - ребёнок — выбор из детей клиента или `+` inline;
   - костюм — поиск по названию / `inventoryCode` **с учётом дат визита** (показывает занятость), либо `+` inline-создание; поле `order.notes`;
   - финансы: «Стоимость аренды», «Внесено» (> аренды — поле очищается), «Осталось» считается сразу;
   - «+ Добавить ещё одного ребёнка» — сразу после выбора клиента; финансы предыдущего заказа для этого не обязательны.
4. **Итоги** визита в реальном времени: кол-во костюмов, аренда, внесено, остаток.
5. Поиск и карточка клиента возвращают `whatsappConfirmed`: доставленное, прочитанное или подтверждённое сообщение доказывает WhatsApp на текущем номере. Поскольку старые уведомления не сохраняют снимок номера, подтверждение действует только если клиент не изменялся после создания уведомления (`client.updatedAt ≤ notification.createdAt`). Для такого клиента форма сразу показывает `exists` без вызова Green-API. Для остальных после выбора/создания клиента и после изменения телефона форма вызывает `GET /clients/{id}/whatsapp-availability` и показывает `exists`, `absent` или `unknown`. Кнопка «Проверить повторно» видна только при `absent` и `unknown`. **«Проверить»** → `POST /visits/preview-code` (резерв `visitCode`) → модалка-превью (`VisitPreviewModal`) с кодом, датами, детьми, суммами и чекбоксом «Отправить WhatsApp». При `absent` чекбокс выключен, сотрудник исправляет номер или сообщает код выдачи лично. При `unknown` визит и отправка разрешены; очередь повторит проверку. Визит можно создать при любом состоянии.
6. **«Подтвердить»** → `POST /visits?sendNotification=true|false`: в транзакции создаются Visit + Orders (+ Notification `pending`), затем job в очередь BullMQ `notifications`. Отправка сообщения асинхронна и не блокирует создание визита.
7. **«Создать новый заказ»** — форма сбрасывается к дефолтам.

Режим **«Быстрая выдача»** использует общие поля клиента, ребёнка и костюма, начинает период занятости в фактическое время подтверждения и предлагает возврат завтра. На странице задаются только возврат (дата и «Вернуть до») и состав заказов с арендой; дата/время выдачи отдельными полями не показываются. Доступность WhatsApp отображается тем же механизмом, что при бронировании; отсутствие WhatsApp или ошибка проверки не блокируют выдачу и не создают уведомление. «Проверить и выдать» проверяет клиента, период и все строки; ошибки видны у полей и в сводке с номером заказа, до успешной проверки код не запрашивается. Модалка «Выдать сейчас» использует общие с обычной выдачей карточки костюмов, блок оплаты/залога и зелёную кнопку «Выдать костюмы», без статуса бирки. Здесь же вводится комментарий. «Получено сейчас» автоматически равно сумме аренды, пока сотрудник не изменил его вручную; ручное значение (включая 0), залог и комментарий сохраняются при повторном открытии. Залог по умолчанию — документ, денежный залог не входит в оплату аренды. Проверка оплаты/залога выполняется в модалке. Подтверждение вызывает `POST /visits/quick-issue`: одной командой создаются issued-визит, заказы с `not_required`, залог, фактический платёж и события истории. Предоплата равна нулю; после успеха показывается уведомление с кодом визита и сразу очищается форма для следующей быстрой выдачи. После неопределённого результата повторяется сохранённое тело с тем же commandId, без пересчёта времени или суммы. Обычный экран возврата подходит без отдельного сценария. Поиск дублей активных визитов и новые проверки уникальности в этом сценарии отложены владельцем.

### 4.2 Незаписанные костюмы (бирки) — `/bookings/unrecorded`
Рабочий чек-лист: заказы с `tagStatus = not_written`. Используется после создания брони, перед выдачей и утром как список задач. Колонки: inventoryCode, костюм, visitCode, ребёнок, телефон, даты, аренда, внесено, пометки. Кнопка **«Бирка написана»** → `tagStatus = written`, строка мгновенно исчезает, без подтверждений. Пустой список: «Все бирки написаны».
В список не попадают отменённые и возвращённые заказы, а также заказы закрытых (`completed`) и отменённых визитов.

### 4.3 Выдача — `/bookings/issue` (`IssuePage`)
- Единый поиск: `1648` → visitCode, `Алия` → ребёнок, `Эльза` → костюм, `C-0128` → inventoryCode, `7707` → телефон. Live, debounce 300–500 мс, минимум 2 символа.
- Таблица «К выдаче» (визиты `reserved`, фильтр по датам) — видна всегда; строка = визит (код, клиент, дети, костюмы).
- Карточка визита: общая информация, заказы по детям с суммами, **финансовый блок**: доплата (по умолчанию = остаток, допускается 0), залог (тип + сумма для cash), комментарий → `visit.notes`.
- **«Выдать костюмы»** → `POST /visits/:id/issue`: все Orders и Visit → `issued`, вся фактическая доплата записывается в `VisitMoneyOperation`, а `finalPayment` остаётся ограниченным распределением по заказам; создаётся Deposit (`returned=false`). Комментарий при выдаче дописывается в `visit.notes` с новой строки, прежний текст сохраняется. Toast «Визит 1648 успешно выдан!» с фактическим кодом визита.
- Отмена выдачи: `POST /visits/:id/unissue`; текущий Deposit получает `deletedAt`, а при повторной выдаче создаётся новый. История залогов сохраняется.

### 4.4 Возврат — `/bookings/return` (`ReturnPage`)
- Такой же единый поиск; таблица «К возврату» — визиты `issued` (строка = визит: код, дети, костюмы, дата возврата, телефон). Индикатора залога в таблице нет — пока визит `issued`, залог по умолчанию у нас.
- Карточка визита: инфо, список костюмов с чекбоксами «Костюм возвращён» (при открытии все сняты; отметки ничего не сохраняют до финальной кнопки — защита от случайного клика), чекбокс «Залог отдали», комментарий при возврате.
- **«Костюмы возвращены»** (при открытии недоступна, становится активной только после отметки каждого костюма) → `POST /visits/:id/complete-return`: Orders → `returned`, Visit → `completed`, комментарий дописывается в `visit.notes` с префиксом `[Завершение]:`.
- Карточка показывает долг или сумму к возврату; при закрытии сотрудник может записать оплату долга/возврат переплаты. Денежная операция не обязательна и не блокирует возврат. После закрытия незавершённые расчёты остаются в отдельном списке, где их можно погасить позднее.
- В той же зоне отдельно — визиты `completed` с невозвращённым залогом (`deposit.returned=false`, `type≠none`); клик → «Забрали ли залог?» → `POST /visits/:id/mark-deposit-returned`.

### 4.5 Уведомления — `/bookings/notifications`
Список отправленных WhatsApp-сообщений со статусами, счётчик «сегодня», поиск. Статусы обновляются в реальном времени через Socket.IO (`notification_status_updated`). Действия: переотправить, исправить телефон и переотправить (через события сокета `resend_notification`, `update_phone_and_resend`).

### 4.6 Костюмы — `/bookings/costumes` («Проверка занятости костюма»)
Список/поиск костюмов (название, inventoryCode), создание/редактирование/удаление. Клик по костюму → read-only окно со всеми периодами занятости (ребёнок, visitCode, телефон, даты), отсортированными по дате начала. «Периодов занятости нет» — без дополнительных выводов. Суммы, залоги и кнопки действий тут сознательно не показываются. Сценарий: пакет без бирки, клиент хочет примерить — сотрудник быстро видит, занят ли костюм.

### 4.7 Клиенты — `/bookings/clients`
Список и поиск клиентов, карточка клиента (дети, история), редактирование, удаление (soft), **добавление в чёрный список / снятие** (`POST|DELETE /clients/:id/blacklist`, с причиной).

### 4.8 Профиль — `/profile`, логин — `/login`.

### 4.9 Все визиты — `/bookings/visits`, карточка — `/bookings/visits/:id`
Отдельный список показывает визиты `reserved`, `issued`, `completed` и `cancelled`; рабочие очереди выдачи и возврата остаются самостоятельными. Поиск по коду визита, клиенту, телефону, ребёнку, костюму и inventoryCode, горизонтальный выбор статуса и отдельный фильтр по дате выдачи. По умолчанию — за всё время; доступны сегодня, вчера, с понедельника и произвольный период. Список загружается с сервера страницами и сортируется по `createdAt DESC, id DESC`; для этого endpoint совпадения не ранжируются.

Вся строка таблицы или мобильная карточка открывает модальное окно; прямая ссылка тоже открывает окно поверх списка. При закрытии сохраняются поиск, период и страница списка. В карточке видны клиент и сроки, заметки, компактные карточки костюмов и текущие активные залоги; действия доступны через меню. История действий и денежные операции объединены: денежные audit-события сопоставляются с журналом по типу и сумме один к одному, при повторяющихся суммах — с ближайшей датой; импортированные платежи остаются отдельными. Предоплата показывается из снимка создания/добавления заказа, а у старых визитов без снимка — без выдуманной даты и автора. Всего получено включает предоплату и активные поступления за аренду; возвраты показываются отдельно. Нулевые долг, возврат клиенту и сумма к возврату скрыты. Денежный баланс показывается только для `issued` и `completed`; в броне показывается остаток аренды без расчёта баланса. `Order.finalPayment` остаётся распределением по заказам и повторно в сумму поступлений не входит. Импортированные старые денежные операции отображаются без даты получения: timestamp миграции не является фактической датой платежа. Идентификаторы заказов/детей/костюмов и `Visit.version` доступны API для редактора, но не показываются сотруднику. Статусы бирки: `written`, `not_written` и `not_required`; последний означает, что бирка для заказа не требуется.

В отменённой карточке история заканчивается причиной отмены и сотрудником. У старого визита без событий показывается предупреждение, что история может быть неполной. Из списка доступны только действия существующих команд, разрешённые текущим статусом визита.

## 5. WhatsApp-уведомления (Green-API)

1. Создание визита с `sendNotification=true` → Notification `pending` → job `send-whatsapp` (`jobId = notification-{id}`) в очередь `notifications`.
2. `NotificationProcessor` проверяет, авторизован ли инстанс WhatsApp (статус хранится в Redis `whatsapp:instance:{id}:status`); если нет — job падает и ретраится.
3. `NotificationService` проверяет актуальный номер через Green-API `checkWhatsapp` перед отправкой. Для клиента с прежним уведомлением `delivered`, `read` или `isConfirmed` проверка не требуется, если после создания этого уведомления запись клиента не менялась: старые уведомления не хранят снимок номера, поэтому условие `client.updatedAt ≤ notification.createdAt` защищает от ложного подтверждения после смены телефона. `exists` → `WhatsappProvider.sendMessage` → `externalId`, статус `sent`; `absent` → статус `noAccount`, без отправки и ретраев; `unknown` → job падает и повторяется позже. Результат `exists/absent` кэшируется в Redis на час по SHA-256 номера, принудительная проверка обходит кэш. Номер и токен не пишутся в логи проверки.
4. Green-API шлёт вебхуки на `POST /webhooks/whatsapp`. Запрос проверяет `WebhookTokenGuard`: заголовок `Authorization: Bearer <токен>` должен совпасть с `GREEN_API_WEBHOOK_TOKEN` (сравнение в постоянное время), иначе 401 без разбора тела. Токен не задан → в `production` 401, в остальных окружениях запрос пропускается с warning в логе. **Настройка:** сгенерировать длинную случайную строку, записать в `.env` сервера как `GREEN_API_WEBHOOK_TOKEN` и ту же строку указать в кабинете Green-API в настройках инстанса, поле «Токен вебхука» (`webhookUrlToken`; то же через метод `setSettings`). Вебхуки:
   - `outgoingMessageStatus` → обновление статуса по `externalId` (только если приоритет выше);
   - `incomingMessageReceived` → клиент ответил → последнее уведомление этого телефона за 48 ч → `isConfirmed`;
   - `stateInstanceChanged` → статус инстанса в Redis.
5. Каждое изменение статуса пушится на фронт через Socket.IO.
6. Текст сообщения — `buildVisitMessage` (код выдачи, дети и костюмы с суммами, итоги, условия: залог от 5 000 ₸, предоплата не возвращается при отказе, график выдачи/возврата, просьба ответить для подтверждения).

`traceId` связывает логи визита, job'а и вебхуков одного уведомления.

## 6. Известные проблемы (подтверждены владельцем как баги/недоработки)

Задачи на их исправление — в [`tasks/backlog/`](../tasks/README.md). Не «чини» их попутно без задачи, но и не опирайся на текущее поведение как на правильное.

1. Нет частичного возврата: костюмы визита возвращаются только все сразу.
2. Проверка занятости учитывает `returned` заказы: костюм, возвращённый раньше срока, остаётся «занятым» до исходной даты.
